# Сравнение: данные на Vercel vs localhost

## Итог сравнения Git vs локальная папка

**Структура файлов:** идентична. Все `web/data/**/all_releases.json` присутствуют и в `origin/main`, и локально.

**Размеры и количество записей:** совпадают.

| Файл | Локально | Git (origin/main) |
|------|----------|--------------------|
| web/data/myfonts/2026-03-10/all_releases.json | 6.4 MB, 1987 releases | 6.4 MB, 1987 releases |
| web/data/myfonts/2026-03-09/all_releases.json | 5.6 MB, 1767 releases | 5.6 MB, 1767 releases |
| web/data/fontstand/2026-03-11/all_releases.json | 1.9 MB, 2431 releases | 1.9 MB, 2431 releases |
| web/data/typenetwork/2026-03-10/all_releases.json | 2.4 MB, 1990 releases | 2.4 MB, 1990 releases |

**Вывод:** в репозитории (Git) лежат те же данные, что и локально. Расхождение с [new-type-livid.vercel.app](https://new-type-livid.vercel.app/) не из-за того, что в git другие файлы.

---

## Почему на Vercel другие данные

**Размер только трассируемых файлов:** в бандл по `outputFileTracingIncludes` попадают только `./data/**/all_releases.json`, `./state/data_coverage.json`, `./config/sources.json`. Их суммарный размер **~35 MB** (всего в `web/data` лежит ~703 MB, но остальное в трассировку не входит). 35 MB укладываются в лимит Vercel 250 MB, так что превышение лимита по одним этим файлам маловероятно.

**Возможные причины расхождения:**

1. **Кэш сборки Vercel**  
   Старый кэш билда подставляет прежние артефакты, и в деплой попадает не актуальная копия `web/data`, а закэшированная (со старыми/меньшими данными). Редеплой без «Clear Build Cache» мог не обновить эти файлы.

2. **Production указывает на старый деплой**  
   В Production может быть назначен не последний деплой (например, старый коммит). Тогда на сайте будут данные из того коммита (785 MyFonts, без Fontstand и т.д.), а в git уже полные данные.

3. **Root Directory = `web`**  
   Если в настройках проекта Root Directory = `web`, при сборке доступна только папка `web`. Тогда `./data` = `web/data` — файлы должны быть там. Стоит убедиться, что в логах билда нет ошибок типа «file not found» для путей из `data/`.

4. **Лимит 250 MB на всю функцию**  
   Если сумма (node_modules + Next + код приложения + ~35 MB данных) превышает 250 MB, билд может падать или подменяться старым успешным. В логах деплоя будет ошибка про размер функции.

---

## Что проверить в Vercel (без правок кода)

1. **Deployments → последний деплой → Build Logs**  
   Есть ли ошибка вида `Serverless Function has exceeded the unzipped maximum size of 250 MB` (или похожая по размеру)? Если да, это подтверждает причину выше.

2. **Deployments → Production**  
   С какого коммита задеплоен текущий production (например, `42cdb17c` или `fe83c408`)? Если с актуального — значит, проблема именно в размере бандла, а не в старом коммите.

3. **Redeploy с «Clear Build Cache»**  
   Уже делали; если после этого данные не обновились при том, что в git они полные, это тоже указывает на лимит или на то, что в бандл не попадают все файлы.

## Отличия localhost vs Vercel (кратко)

| Аспект | localhost | Vercel |
|--------|-----------|--------|
| Откуда читаются данные | Файловая система: `web/data/`, `web/state/` | То же, но только файлы из serverless-бандла (трассировка) |
| Кэш сборки | Нет | Возможен старый кэш → в бандл попадают старые копии файлов |
| Итог | Все источники и даты (MyFonts 1987, Fontstand 2431, 9–15 марта и т.д.) | Часть данных (785 MyFonts, нет Fontstand, нет 9–15 марта) — как в старом деплое или из кэша |

## Дальнейшие шаги (когда будете менять код)

Если окажется, что причина в размере бандла или в кэше, варианты:

- Вынести данные во внешнее хранилище (S3, R2, Vercel Blob) и подгружать по запросу.
- Убедиться, что при деплое всегда используется «Clear Build Cache», или отключить кэш для папки с данными (если Vercel это позволяет).

## Prebuild и корневая папка `data/`

В репозитории в `.gitignore` указано **`/data/`** — то есть папка **`data/` в корне репо не коммитится**. В git попадает только **`web/data/`**.

При деплое на Vercel (Root Directory = `web`):

- В клоне есть только `web/data/` (из коммита).
- Путь `../data` (родитель от `web` → `data`) в таком клоне **не существует**.
- В `sync-runtime-data.mjs`: `sourceDataDir = path.join(repoRoot, "data")` = `../data` → **такой папки нет**.
- Скрипт выводит: **«Source data/ not found in repo root. Keeping existing web/data as-is.»** и **не перезаписывает** `web/data`.

То есть на Vercel prebuild не подменяет `web/data` корневой `data/` — должны использоваться файлы из git (`web/data`). Если в логах билда на Vercel видно **«Synced data/ from repo root»**, значит в среде сборки по какой-то причине есть `../data` (например, кэш или другая конфигурация), и тогда в прод попадает не то, что лежит в `web/data` в репо.

**Что проверить в логах деплоя:** в шаге `prebuild` (или `node scripts/sync-runtime-data.mjs`) какая строка выводится:
- **«Synced data/ from repo root»** → тогда на проде используется не `web/data` из git, а скопированная корневая `data/` (источник расхождения).
- **«Source data/ not found... Keeping existing web/data as-is.»** → тогда причина не в prebuild, а в трассировке/бандле (см. ниже).

## Трассировка Next.js (outputFileTracingIncludes)

Файлы в бандл серверной части подтягиваются по шаблону `./data/**/all_releases.json`. Если корень проекта на билде — каталог `web/`, то должны попасть все такие файлы из `web/data/`.

Полезная проверка **локально** (без правок кода): из каталога `web/` выполнить `npm run build` и посмотреть, сколько файлов попали в трассировку для главной страницы, например:

```bash
cd web && npm run build
# после сборки:
find .next -name "*.nft.json" -path "*app*page*" 2>/dev/null | head -1 | xargs cat 2>/dev/null | grep -o 'all_releases.json' | wc -l
```

Если число совпадает с ожидаемым (например, 24 файла `all_releases.json`), трассировка локально в порядке; если на Vercel при этом данные другие — возможна иная раскладка путей или кэша на их стороне.

Текущий документ фиксирует сравнение git vs локальная папка и возможные причины расхождения с Vercel без изменений в коде.
